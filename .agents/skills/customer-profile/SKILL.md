# 客户档案与分层

接令时按[A卷上岗原则](../private-domain-ops/references/a-volume-onboarding.md)核对事实、真实问题与失败路径；按风险调整留证，同一任务复用已完成判断与有效授权。

本场景停止条件：身份冲突不合并正式档案，未知不写成事实或同意。只拒绝某活动不扩大成全局拒联，营销拒联不取消客户主动请求且已获授权的必要售后；跨角色只传任务所需字段。参照[拒联范围](../private-domain-ops/references/failure-cases.md#case-08)、[客户资料范围](../private-domain-ops/references/failure-cases.md#case-09)。

输入：企业与账号范围、稳定客户 ID 或待匹配引用、获授权的记录、已有档案与标签规则。

1. 先核实身份。只有昵称时可以建立待匹配草稿，不合并、不写入正式客户记录。跨渠道合并需可信的身份对应证据。
2. 按[档案结构](references/profile-schema.md)记录事实、推断、待确认、来源、更新时间和负责人。近似预算保留原话及精度，金额注明币种。未知保留 null；只有确认没有时才填空数组。
3. 使用客户自己的标签字典。标签记录可观察行为或明确需求，避免“易怒”“好说话”等无依据的人格判断。参考[标签体系](references/tag-system.md)。
4. 按五个独立维度记录生命周期、当前购买意向、营销联系范围、互动状态和服务状态。复购客户仍可能正有高意向；历史购买不推出本次意向。只拒绝某次活动不扩大为全局拒联；明确拒绝营销则停止该范围营销，必要售后仍按客户请求与服务授权处理。未知不推断为同意。
5. 输出增删改 diff 及每项依据。迁移旧 stage 时保留 legacy_stage、原来源与时间，不按词面拆出未经证明的状态。冲突记录并存并标时间，不能仅因新记录较近就覆盖来源更可靠的事实。
6. 实际写入、合并或标签删除必须有相应授权与已适配入口，按[授权规则](../private-domain-ops/references/authorization.md)处理。写后回读字段；无入口时保留可导入草稿。

输出：客户引用、变更 diff、依据、未解决冲突、写入状态、下一步。完整客户资料留在客户批准的业务环境。
