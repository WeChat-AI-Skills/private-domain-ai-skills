## 三个场景的合成验收

每组由新上下文 Agent 使用隔离安装副本逐轮作答，答复落盘后才读取下一轮观察。另一个新上下文独立核对冻结轨迹和预先制定的判据。输入均为虚构，观察由演练提供，未调用真实 SCRM 工具。

| 用户要求的场景 | 观察到的实际合成行为 | 结果 |
| --- | --- | --- |
| 只换一张图 | G1 R1–R4：朋友圈及好友消息都按原 ID 打开修改、仅换首图；收到保存提示后仍重开同一 ID。两条均逐字段核对原账号、可见范围/收件人、时间、其他内容与排版未变，仍为已排期未执行 | 通过 |
| 找不到修改或保存后读回不一致 | G2 R1–R5：朋友圈缺修改入口时保留原任务并报告；好友消息保存超时先查原 ID，发现旧第二行和空行丢失后停止并报告。未点击配置页“提交为新任务”；显式保存失败另有独立反事实分支，亦停止变更 | 通过 |
| 整批更换收件人且原任务无法修改 | G3 R1–R2：核对名单字段不可改，形成含原 ID、变更范围和证据的负责人报告，保留原任务等待决定；同时覆盖整体换发送账号 | 通过 |

G3 R3–R6 额外检查：明确批准取消并重建后，取消请求受理或超时仍先回查；“取消处理中”或“已取消但执行状态未知”都不允许重建。只有旧任务同时确已取消且未执行后才进入替代任务准备。演练没有提供新建回执，因此未宣称替代任务已创建。
